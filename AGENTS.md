# AGENTS.md

## Project

Butler: real-time messaging layer so coding agents (Codex, OpenCode) can talk to each other and share session-level context. Design: Go backend server (M1), MCP server for agents (M2), web panel (M3) — all done. See README for the API contract, MCP onboarding, and panel usage.

## Commands

- Run server: `go run ./cmd/butler serve` (or build `./cmd/butler`)
- Run MCP server: `go run ./cmd/butler-mcp --server URL --token TOK` (stdio)
- Run codex relay: `go run ./cmd/butler-mcp relay --workdir DIR` (long-poll butler → `codex queue`; see `cmd/butler-mcp/relay.go`)
- Build: `make` (both binaries into the repo root; `make butler` / `make butler-mcp` individually, `make BIN_DIR=dist` elsewhere); `make check` = vet + test; `make fmt` formats; `make help` lists targets; `make clean` removes the binaries
- Test: `go test ./...`
- Vet: `go vet ./...`
- CLI: `butler kind add|rotate|list` (one token per agent kind), `butler agent list|revoke` (registered instances), `butler reset [--yes]` (move the DB aside and recreate it empty; refuses while the server is listening; admin token file is untouched) — flags work before or after the positional id

## Layout

- `cmd/butler/` — server binary; subcommands `serve`, `agent`, `version`
- `cmd/butler-mcp/` — stdio MCP server for agents; flags/env `--server`/`BUTLER_SERVER`, `--token`/`BUTLER_TOKEN`, `--state-file`/`BUTLER_STATE_FILE` (writes `<workdir>/.butler/instance.json` after registration); `relay` subcommand (`cmd/butler-mcp/relay.go`) = the codex-side push-delivery daemon: long-polls as the state-file identity and injects via `codex queue`
- `internal/store/` — SQLite via `modernc.org/sqlite` (pure Go, no CGO); one embedded `schema.sql` applied with `CREATE ... IF NOT EXISTS` on open (no migration history — see Gotchas)
- `internal/api/` — REST + long-poll handlers, auth middleware, Go 1.22+ pattern routing
- `internal/hub/` — in-process wake-up fanout; per-agent subscribers (long-poll `wait`) and per-session subscribers (panel SSE)
- `internal/mcpserver/` — MCP tool handlers + typed HTTP client for the API
- `internal/ui/` — embedded web panel: html/template + first-party vanilla JS (no htmx, no build step), SSE stream, admin-token login, posts as the `admin` agent (id `admin`, kind `human`, display name `Admin`)
- `.opencode/plugins/butler/` — OpenCode relay plugin: one butler **role** per OpenCode session, eagerly activated (startup role list + session-view/message events), each relaying into its own session; the agent client stays backend-only (see Conventions)
- `internal/auth`, `internal/ids`, `internal/metrics`
- `deploy/nginx.conf.example` — reverse proxy config for remote deployment

## Conventions

- Identity model: one token per agent **kind** (`kinds` table, CLI `kind add`). A client registers (`POST /api/v1/register` with kind token + hostname + workdir) and gets back a server-minted **UUID identity** (`ids.UUID()`, the only identity — it never changes and carries no derived meaning) plus an instance token. Registration key = (kind, hostname, workdir, **client_session**); same key → same UUID. Display names are labels, not identities: a per-session **sibling** (non-empty client_session, registered via an instance token — see below) is labeled with the body's `display_name` (the client session's title), everything untitled (app-level identities) with its own UUID; both are refreshed on re-register and via `POST /api/v1/agents/rename`. One live instance per identity: re-registering revokes the previous instance's token (`ReplaceAgentToken`, last login wins). App-level replacements announce (system message) in every joined session; sibling replacements are silent (the plugin re-registers them every app restart). `agent revoke` / panel kick / `POST /api/v1/agents/{id}/revoke` **evict** an identity: tokens revoked + `removed_at` set — hidden from listings, participants and mentions, with a system notice per joined session. Every server-generated notice — join, eviction, replacement — names the agent by its **display title** (`store.NoticeLabel`: display name, id fallback; `JoinSession` resolves it inside its transaction), so the panel never shows a UUID as a label or in a notice body; like mentions these are text snapshots, so a later rename does not rewrite stored notices. The row survives (soft removal: `messages.sender_id`/`sessions.created_by` reference agents without cascade); re-registering the identity revives it (`ClearAgentRemoved`), so kicks stick for stale agents and only disconnect live ones until their next registration.
- **Agent clients, roles, meetings** (the user-facing vocabulary for the OpenCode integration): the app-level identity is the **agent client** (backend-only), its per-session siblings are **roles**, and a butler session composed of roles + admin is a **meeting**. Once a client has at least one live (non-removed) role, store `ListAgents`/`Participants` hide the client (SQL `clientHidden(alias)` — display-only: auth (`GetAgentByTokenHash`), delivery (`MessagesSince`), registration (`FindInstance`) and revival paths never filter on it), so the panel, session picks, participant rows and mention resolution see roles only; with no live roles left the client re-appears as the visible fallback. The CLI `agent list` always shows everything. `GET /api/v1/agents/roles` (instance-token auth) returns the caller identity's roles with a `removed` flag — the plugin's eager-activation feed.
- Sibling registration (`api.registerAgent` instance-token path): an instance token may register siblings of its OWN identity only — kind/hostname/workdir are inherited from the caller, the body supplies `client_session` + `display_name` (the client's session title). This exists because the OpenCode plugin can see the app instance token in `.butler/instance.json` but never the kind token. Display titles are followed separately via `POST /api/v1/agents/rename`: instance token + `{client_session, display_name}` renames a sibling of the caller's identity (the plugin pushes OpenCode session title changes here, throttled to ~30s per session); admin + `{agent, display_name}` renames anyone. Ids never change.
- Global session: fixed id `global` (title "Global", `store.GlobalSessionID`), created at server start / reset by `EnsureGlobalSession(ctx, "admin")` + joined by every existing agent in `bootstrapGlobalSession` (join notices only on the first actual join). It is **fixed**: `store.SetSessionStatus` and `store.DeleteSession` refuse it (`ErrConflict`), so no panel, API or CLI path can archive or delete the room every agent is in. `registerAgent` auto-joins every registering agent (idempotent — re-registration is a no-op) and fans out. Agents can be in any number of sessions; `wait`/`check`/`catchup` aggregate across all joined sessions via the participants subquery.
- @mentions: `store.InsertMessage` resolves the `@tokens`/`@names` in the content against the **session participants** — exact agent id, agent kind (`@codex` = every codex participant), exact display name (case-insensitive, spaces allowed: `@Fix read marks` — the readable form the panel inserts; at each `@` the longest matching participant title wins via `store.mentionedNames`, and untitled identities fall back to their id), or `@all`/`@everyone`/`@here` — persisting the resolved agent ids in the `messages.mentions` column (JSON array). Consumers differentiate urgency via `Message.MentionsAgent(id)`: MCP `wait_for_messages`/`check_messages` print a counts header ("N @-mention you (reply expected), M FYI") plus a `(mentioned you)` line marker and group by session; the codex daemon frames injected prompts `ADDRESSED TO YOU (reply expected):` vs `FYI:`, while the OpenCode plugin enqueues a **pointer instead of the messages** (see Push delivery below): no per-message framing, and the agent gets the same split from `read_session`/`check_messages` when it reads. System/context notices never contain mentions (contents are server-generated). Mentions only resolve within a session's participants — mention someone not in the room and it records nothing — and the author is never mentioned by its own message (`resolveMentions` skips `sender_id`): mentions mean "agents that should reply", so a role quoting its own title/id, or any plain `@all`, would otherwise self-resolve and show up as "(mentioned you)" in its own wait output. A backslash-escaped `\@` is literal (`isEscapedAt`, an even number of backslashes escapes nothing), so a message about mentions — a doc, a report, an explanation of the syntax — can quote `\@all` without addressing the room. Names are resolved at insert time: renaming a role does not rewrite already-stored mentions.
- Keep dependencies minimal: stdlib first; new deps need a strong reason.
- Message ordering: `messages.global_seq` (SQLite AUTOINCREMENT rowid) is the universal cursor; clients long-poll `GET /api/v1/wait?after=<seq>`.
- After any message/context/join write, fan out to BOTH hub subscriber kinds: `Hub.NotifySession(sid)` and `Hub.Notify(participantIDs)` — see `api.notifySession` / `ui.fanout`.
- Store uses MaxOpenConns(1); writes are serialized. WAL + busy_timeout let the CLI subcommands touch the DB while the server runs.
- Tokens are SHA-256 hashes at rest; admin token lives at `~/.config/butler/admin-token` (0600); agent tokens are only printed at creation/rotation.
- Message inserts are idempotent via client-supplied `id` (`ON CONFLICT DO NOTHING`).
- Panel agents table: columns are presence dot, **Kind**, **Title** (display name; the id as a small sub-line when it differs — @mentions resolve against the id *and* the title), host, workdir, seen, and a **kick** button (`POST /panel/agents/{id}/revoke`, admin-form + same-origin) that evicts the agent (tokens revoked + hidden from participants and listings immediately — see Identity model; the eviction notice names the agent's display title, so panel tests assert on the notice text and on the absent kick form/pick rather than on the title's absence from the page). `admin` is never kickable and always shown online (`ui.agentOnline` / `api.toAgentJSON`): it never authenticates via the agent API, yet a presence reader is by definition at the panel. Presence is the 90s window everywhere (`online()` in ui, `presenceWindow` in api) — including the participants fragment (SSE `presence` events re-send it periodically).
- Panel session creation: dashboard form (`POST /panel/sessions`, form-encoded `title` + repeated `agents` values) creates the session as `admin` then `JoinSession`s each picked agent so they get join notices; validation mirrors the API (title required ≤200, unknown agents 400). Composer @-autocomplete is fed by a `data-mentionables` JSON attribute on the textarea (the other participants' display titles, deduped, + `all`; `admin` excluded, ids only when a role has no title) and `app.js setupMentions` writes `@<title>` — the server resolves titles too, so the menu never has to expose a UUID. `store.Participants`/`store.ListAgents` order by `display_name COLLATE NOCASE` (UUID ids would look random) — the panel sidebar, agents table, session picks and the add-participant picker all inherit that order.
- Panel add-participant: the session view's **Add to meeting** picker (`POST /panel/sessions/{id}/join`, form-encoded `agent`) adds one role to an existing session — reuses `store.JoinSession` (participant row + "joined the session" system notice in one transaction) + `ui.fanout` (wakes the role's wait loop and every panel via the SSE presence event, which re-renders the `participants` fragment). `sessionViewData.Addable` (built by `ui.addableAgents` from `ListAgents` minus current participants) feeds the picker, so hidden agent clients and evicted agents are never offered; the handler re-validates with `store.GetVisibleAgent` (same visibility rules as list/participants) and rejects unknown/evicted/hidden agents, `admin` and existing participants with 400, non-active sessions with 409, then 303s back to the session. `store.JoinSession` enforces "active sessions only" itself (session status read in the same transaction, `ErrConflict` → 409, no participant row and no notice written), so the API's `POST /api/v1/sessions/{id}/join` — which had no status check of its own — is covered too; `registerAgent`'s auto-join of the always-active global session is unaffected.
- Panel remove-participant: every row of the shared `participants` fragment carries a small ✕ (`POST /panel/sessions/{id}/participants/{agent}/remove`, `confirm()`-guarded, 303 back to the session) on active sessions only — hidden when archived, refused (409) if called anyway. `store.RemoveParticipant(ctx, sid, agentID, actorID)` is the mirror of `JoinSession` (same "active sessions only" rule, `ErrNotFound` for a missing session or membership) and does its work in one transaction: delete the participant row, delete that agent's `read_marks` row for the session (a non-participant has no cursor, so a re-join starts unread) and insert a notice naming the actor — `<label> left the session` when `actorID == agentID`, else `<label> was removed from the session by <actor label>` (`noticeLabelTx` is the shared in-transaction title lookup `JoinSession` uses too). The agent is not evicted: row intact, other sessions intact, re-addable with the picker. The API counterpart is `DELETE /api/v1/sessions/{id}/participants/{agent}` (admin, the session creator, or the agent itself; admin-token removals are attributed to `api.adminAgentID`). The fragment's data is `participantsView{SessionID, CanRemove, Agents}` — the session page and the periodic SSE `presence` re-send both build it, the latter re-reading the session status so a join, removal or archive reaches every open panel within one heartbeat (15s); messages (like the removal notice) stream immediately.
- Panel session lifecycle: dashboard rows carry **archive**/**reopen** and **delete** as icon buttons (`POST /panel/sessions/{id}/status`, form `status`; `POST /panel/sessions/{id}/delete`, `confirm()`-guarded), both landing back on the dashboard **with a one-shot notice** — the panel login entry (`ui.sessionStore`) carries a `notice` that the next dashboard render takes and clears (`ui.panelNotice` → `dashData.Notice` → `<p class="notice">`), so an archive, reopen or delete states its outcome ("Session “X” archived.") instead of leaving the user to infer it from a row they may not recognise. A lifecycle action on a session that **no longer exists** — a stale dashboard row (deleted from another tab) or a repeat submit — is not an error: the panel reads the session first (the title names the notice) and treats the intent as already satisfied, redirecting with "That session no longer exists…" (`ui.sessionGoneNotice`) rather than a bare `not found`; both forms also disable their submit button on submit (`onsubmit`) so a double-click cannot send the second request. Every panel error path (`ui.httpError`, incl. `storeErr` and the session page of a deleted session) renders `error.tmpl` — status text, the message, a back link — under the error's status code, never a bare text body: a browser can arrive there from a stale tab, a bookmark or a dead session link. the session page itself has no lifecycle controls, only a title row with the back link and a status badge. The icons are inline `{{define "icon-archive|icon-restore|icon-trash|icon-lock"}}` SVG fragments in `fragments.tmpl` (no icon font, no build step), and the words live in `title`/`aria-label`. The fixed global session shows a lock (`fixed-ico`) instead of actions. Archiving freezes a session: posts, context writes and joins already 409 on a non-active session (API *and* panel), and the session page swaps the composer, the add-participant picker and the context form for an archived banner pointing at the sessions list. Delete is `store.DeleteSession` — one transaction that collects the participant ids (returned so the caller can `Hub.Notify` their wait loops and `NotifySession` any open stream) and then deletes messages, read marks, participants and context items before the session row: `messages.session_id` carries no cascade (history) and `read_marks` has no FK at all, so both are explicit while `participants`/`context_items` cascade. There is no soft-removed row and no undo (unlike a kick). `store.SetSessionStatus`/`DeleteSession` refuse the fixed `global` session with `ErrConflict` → 409, so no path (panel, API `DELETE /api/v1/sessions/{id}` — creator or admin, like PATCH — or CLI) can archive or delete it; `newTestAPIGlobal` gives API tests the real-world global session.
- Read marks (`read_marks` table): per-agent per-session cursor of the highest seq the agent has **received**. Advanced by `api.markReads` whenever the server delivers messages to an agent — wait batches (`waitMessages`), session message fetches (`sessionMessages`, incl. MCP `read_session`), and own posts — then wakes ONLY `Hub.NotifySession(sid)` (never `Notify`: read advances must not churn long-poll waiters). The panel renders `✓k/N` per chat message via `ui.loadReadState`/`attachReadState` → `uiMsg`: **N is the message's audience** — every other participant who was already in the room when it was sent — and k the audience members whose read state covers it, green `.all` at k=N. The **human is part of both**: `admin` has no cursor by design (`store.SessionAudience` reports `kind`, the panel flags `AdminAgentID` as `human`), but a mark is only ever visible to the human, so seeing it means having seen the message — crediting the human needs no cursor, and a stored one would change nothing observable. Membership is pinned to a **message seq, not a clock**: `store.SessionAudience` carries each member's `JoinedSeq` (the seq of its latest join notice — `joinedNoticeSuffix`, shared with `JoinSession` — or 0 for the creator and creation-time participants, who have no notice and were there from the start), so a member who joined later is not part of an older message's audience; without it an ever-growing room (Global) would show every old message stuck below N/N. The same `uiMsg` carries the sender's **display name** (the session title) plus both groups for the mark tooltip (`read by X · not yet: Y` via `ui.readTip`), so the message list never shows a UUID unless an identity's display name *is* its id (`data-sender` and the `<b title>` tooltip keep the id for the read-mark math and as the identity reference; a sender no longer in the session — a kicked agent's history — is resolved from its surviving agents row, not left as an id). The page embeds `data-audience` (members: id, name, since, human) / `data-reads` JSON on `#messages` and the SSE stream emits `reads` events (`stream` handler diffs cursors on wake) plus an `audience` event on the presence heartbeat (so a join/removal moves N and the tooltips within one heartbeat, not only on reload) which `app.js updateReadMarks` applies live — the client mirrors the server's rule exactly (human always a reader, `since` > seq excludes).
- Agent etiquette: ack-then-work-then-report. `mcpserver.formatNotification` and the wait tool description tell agents to send a brief ack (send_message) as soon as they decide to act, then do the work, then report — never stay silent through a long task.
- Push delivery to OpenCode: `butler-mcp` writes `<workdir>/.butler/instance.json` (atomic temp+rename, 0600, agent + instance token + server URL) on every registration — last registrant owns the file; readers re-read it on 401. The relay plugin (`.opencode/plugins/butler/`) builds **one butler role per OpenCode session**, activated EAGERLY: at startup it lists the agent client's roles (`GET /api/v1/agents/roles`) and re-registers each one whose session still exists (evicted roles skipped — they stay out until their session acts; deleted sessions fail `ctx.session.get` and are skipped), and any session touch — model request (context hook), `session.viewed`, `session.inbox.enqueued` — activates its role (once titled) via the instance token (see Sibling registration above). `waitForTitle` skips sessions whose `location.directory` differs from the plugin's (they belong to another agent client). Each role runs its own `/api/v1/wait` loop and relays each batch into ITS OWN session only (`ctx.session.prompt(..., delivery: "queue")`) — so @mentioning that role (by its id, or `@opencode` for every role of the kind) wakes exactly that session. The relay **enqueues a pointer, not the message content** — `[butler] new messages in "<title>" (<sid>)` plus the instruction to read them with the butler MCP tools (`read_session`, `check_messages`) — because pasting content queued unbounded turns of stale text that those tools can fetch on demand. Enqueueing is **deduped per (OpenCode session, butler session)** off the plugin's **event stream** (the plugin context does not expose the inbox HTTP API): `ctx.event.subscribe()` delivers `session.inbox.enqueued` for every enqueue — with the item's `inboxID` and its text — and `session.inbox.delivered` with that `inboxID` the moment the item's turn starts (and `session.inbox.cancelled` when an interrupt takes it out of the queue), so the plugin sets a pending pointer on the first and clears it on either of the others (5-minute TTL bounding an event it never saw). The new notification is **dropped** while one for that session is still pending — the queued pointer already means "read this session" and picks up everything that arrived since. One pointer is armed **per (OpenCode session, butler session) per relayed batch** and the relay only runs on a non-empty fresh batch (`relayInto`'s `sids` loop, gated by `notifyQueued`; the loop gates on `if (todo.length > 0)`), so a pointer always carries **at least one seq the loop had not relayed** — and a batch carries several messages, so messages-per-pointer is ≥1 with **no upper bound** while pointers-per-(session, batch) is ≤1. "Fresh" means not yet relayed **by the loop** — its cursor plus the in-memory `delivered` claim — **not unread by the agent**: `read_session`/`check_messages` advance neither of those (they advance the *server's* read marks, a different cursor), so an agent that reads out of band (a verifier reading the room, an eager poller) legitimately sees fewer new messages than the plugin relayed, and a pointer with nothing new *to the agent* is not a dedupe failure (the only such case is a replay after a teardown). The check **fails open** (anything never observed counts as not queued): suppressing a notification loses a message, while a duplicate only costs a turn. Session title changes are pushed via the rename endpoint (~30s throttle). The agent-client loop (shared identity → most-recently-active session, or a "Butler" bridge session with `bridge: true`) keeps serving sessions without their own role; a per-seq `delivered` map dedupes — loops claim `(seq, target)` pairs synchronously BEFORE the async relay (whoever claims first delivers; claiming after would race double-delivery). The plugin also **shadows the butler MCP tools** under their effective names (`ctx.tool.transform`: remove `butler_*` ids, re-add its own with `options: {namespace: "butler", codemode: true}`); executors resolve `context.sessionID` → that session's agent, falling back to the app identity for unregistered sessions / no session context. Cursor semantics match butler-mcp for the agent-client loop: initialized to the server's latest seq at loop start, old messages are never replayed. **Role loops persist their cursor** in plugin storage (`ctx.storage`, key `butler:cursor:<sessionID>`) and persist it only after a batch is relayed (at-least-once): OpenCode tears plugin contexts — and every wait loop with them — down when no client work is active, so a role that was offline while messages arrived delivers that backlog on its next activation instead of skipping it. The cursor indexes the server's message stream, so it is **clamped to the server's current seq** — fetched at loop start and (for role loops, every ~10 idle polls) while running: a server-side reset (`butler reset` recreates the DB, seq restarts at 0) leaves a persisted cursor far ahead of the fresh stream, which silently starved every role with no error until the stream regrew past it. A detected reset replays the fresh stream from seq 0 (the role's read marks died with the old DB) and persists that immediately; a genuinely stale-but-behind cursor is kept (that backlog is what the dead window missed). The agent-client loop deliberately does NOT persist (forward-only), so sessions with live roles never get double delivery — it detects the same reset and skips forward to the server's position instead of replaying.
- Push delivery to codex: same state file, different consumer — `butler-mcp relay --workdir DIR` (in `cmd/butler-mcp/relay.go`) long-polls as the codex identity and injects each batch with `codex queue --thread <id> --message <text>`. Codex's shared app-server daemon persists queued messages (`~/.codex/queue_1.sqlite`): live sessions receive them at the next turn boundary, closed sessions on resume. Target thread = most recently modified rollout under `~/.codex/sessions/` whose first-record `payload.cwd` matches the workdir (`thread_id` on old rollouts, `id` on new ones). Delivery failure does NOT advance the cursor (batch retried until a thread exists). One relay process per workdir.
- Panel UI is html/template + first-party vanilla JS embedded via go:embed — deliberately no htmx/React/node toolchain. Keep it that way unless there's a strong reason.

## Gotchas

- go.mod requires Go 1.26.1.
- CSS class collision: message kind classes are rendered on `.msg` divs (`msg chat`/`msg system`/`msg context`), so layout CSS must NEVER use a bare `.chat` selector — it would hit every chat message too. The chat column is `.chat-pane` (this exact collision once gave each message `min-height: 70vh`, filling the whole pane). Same for any future kind value: check `fragments.tmpl` before naming a layout class.
- The `message` fragment template reads `.ReadCount`/`.ReadTotal`/`.Readers` (only on the `uiMsg` wrapper): passing a bare `store.Message` fails template execution and silently drops the message. All render sites (`sessionView`, panel `postMessage`, SSE `stream`) go through `attachReadState`. `sessionViewData.Agents`/`.Reads` must marshal non-nil (empty `"[]"`/`"{}"`, never `null`) — `app.js` parses them into maps.
- Read-cursor wakes: `api.markReads` calls only `Hub.NotifySession` — waking long-poll waiters on every read advance would turn each agent poll into a wake-up storm.
- Schema changes: edit `internal/store/schema.sql` (the single embedded schema; `ensureSchema` applies every statement with `CREATE ... IF NOT EXISTS` on open). There is deliberately **no migration history**: butler is pre-release, so changing the schema means recreating the database (`butler reset`) — never upgrade an old database in place, and don't re-add migration machinery without a reason.
- Server binds 127.0.0.1:8787 by default; remote deploys sit behind an HTTP reverse proxy (buffering off, read timeout > wait timeout — see deploy/nginx.conf.example).
- Long-poll `wait` handler re-checks the DB after subscribing to avoid the missed-wakeup race — preserve that pattern when touching it; the panel SSE `stream` handler uses the same pattern.
- Every hub subscriber cancel runs in the request goroutine that owns it (a wait batch, an SSE stream returning), not under the hub lock the subscribe held — so `Hub.addSub`'s cancel closure must take `Hub.mu` itself. Without it, the delete races `Notify`/`NotifySession` (and other cancels) and the runtime answers with `fatal error: concurrent map writes` / `concurrent map iteration and map write`: a fatal error is not recoverable per request, so it **kills the server process** — agents then see `connection refused`, `butler-mcp` fails registration and OpenCode latches its MCP to "failed" until the transport is re-established (an outage that looks like "OpenCode disconnected", not like a crash). This actually happened repeatedly (5 fatal dumps in one log); `TestConcurrentSubscribeCancelNotify` reproduces it and `make race` guards it.
- Go's `flag` stops at the first positional arg; `cmd/butler` uses a rotation loop (`parseSubFlags`) so `kind add <id> --name x` works. Keep that in mind for any new CLI subcommand.
- `butler-mcp` speaks MCP on stdout — never log or print to stdout there (logs go to stderr).
- `butler-mcp` registers at startup with a kind token (hostname/workdir defaults: `os.Hostname()` / cwd) and swaps its client to the returned instance token BEFORE serving tools — `Client.SetToken` is not concurrency-safe, keep that ordering.
- `butler-mcp` keeps its message cursor in memory, initialized to the server's latest seq at first poll: restarts intentionally skip old messages; agents use `read_session` for history. `send_message`/`set_context` advance the cursor past their own messages to avoid self-echo.
- The relay plugin and the MCP tools are two consumers of one identity: if you run `butler-mcp` manually with the same (kind, hostname, workdir) to refresh `.butler/instance.json`, the running MCP's token is revoked (401) until the client restarts it — expected, not a bug. Session agents are unaffected (they hold their own sibling tokens).
- Two OpenCode windows in the same directory are fine: every session has its own butler agent (own wait loop, own relay target). Only the app-level identity is single-live-instance — the losing window's MCP tools 401 until it re-registers, but the plugin's shadowed tools still work per session (session-agent tokens are independent). Duplicate relay into one session is prevented by the `delivered` claim map, not by single-instance semantics.
- Deleting an OpenCode session leaves its butler agent behind (loop stops, agent stays a participant with a dead token) — kick it from the panel: that evicts it for good.
- Kicks must stick: the plugin never re-registers a session agent in response to a 401 (its wait loop and `api()` both stop and drop the entry instead) — auto-recovering there would resurrect every kicked agent within seconds. A session agent only comes back via `ensureSessionAgent` on the session's next model request; the app-level identity only via a butler-mcp restart (the plugin cannot re-register it — it never sees the kind token).
- Plugin context lifetime: OpenCode tears plugin contexts — and every butler wait loop with them — down when no client work is active. The `opencode serve --service` process staying alive does NOT keep roles polling: a role simply shows offline (90s presence window) while its loop is dead, and re-activates on the next plugin load (eager activation). Role cursors persist in `ctx.storage` so the dead-window backlog is delivered on revival; the agent-client loop stays forward-only so backlog is owned by role loops (persisting both would double-deliver into sessions with live roles).
- Eager activation's 401 path must check the state-file token actually **changed** before retrying: re-reading the same dead token and `continue`-ing spins at request speed — after one `butler reset` it hammered `GET /api/v1/agents/roles` ~2000 times a second for a minute (105k requests, gigabytes of log) with a store that serializes on one connection. An unchanged token now falls through to the loop's 30s backoff (same rule as the client `wait` loop, which sleeps 1s before retrying). Expect loss of the app identity after a reset until `butler-mcp` re-registers (it holds the kind token; the plugin never sees it) — the plugin's roles are unaffected, they re-register with their own instance tokens.
- Plugin notification dedupe rides on the **event stream**, not the inbox API: the running plugin context exposes neither `ctx.inbox.list` nor `ctx.session.inbox.list` (`ctx.session` has no `inbox` key at all — probed in a throwaway location, so don't reintroduce a probe on the strength of the HTTP route existing), while `ctx.event.subscribe()` delivers `session.inbox.enqueued {sessionID, inboxID, item.payload.text, delivery}` plus `session.inbox.delivered {sessionID, inboxID}` (the item's turn started — watched live: an enqueued item delivers immediately when the session is idle, and only when its turn comes round when the session is busy) and `session.inbox.cancelled {sessionID, inboxID}` (an interrupt takes pending items out of the queue — also watched live, and the reason a cancel must **settle** the registry entry: without it that session's notifications stay suppressed until the TTL, which the first live test reproduced as a dropped notification). The plugin keys a pending-pointer map by `inboxID` (enqueued → set, delivered/cancelled → delete, `NOTIFY_TTL_MS` bounding an event it never saw) and drops a new pointer while one for the same (target, butler session) is still pending. The queued pointer is deliberately **staleness-proof**: it carries no message count and no per-batch "N @-mention you" claim, because a dropped (already-queued) notification would understate what has arrived since; the urgency rule lives in one generic sentence, and the real counts come from `read_session`/`check_messages` when the agent reads. Diagnosing the plugin: its `console.*` does **not** reach `~/.local/share/opencode/log/opencode.log` — it goes to the stderr of the process that started the server, i.e. a terminal (`lsof -p <pid> \| grep 2u` shows `/dev/ttysNNN`), so watch that terminal or relaunch with `2>butler-plugin.log`; the dedupe itself needs no logging to work.
- `butler-mcp relay` targets the most recently active codex session in the workdir — if codex has never run there, delivery retries without advancing the cursor (by design, at-least-once). Don't run two relays for one workdir: both would queue every message (duplicates).
- `codex queue` accepts any thread id known to the daemon, but delivery into a *running* session requires that session to be connected to the shared app-server daemon (CLI TUI / `codex exec` are). Headless `codex exec` may fail with account/model errors unrelated to queueing (e.g. `gpt-6.1-sol` via ChatGPT login) — the relay itself only needs the `codex` binary on PATH.
- Panel fragment templates (`fragments.tmpl`) are rendered for both normal pages and SSE data — keep them valid single templates and remember SSE re-sends them as `data:` lines.
- Panel login sessions are in-memory (lost on restart by design); login cookie is scoped to /panel.
- The sibling Rust port (`../butler-rs`) is a frozen snapshot of the pre-mentions design, kept unchanged on purpose (it exists to compare implementations, not to track features). The two have diverged: butler has the single-schema reset model, the global session, panel session creation, mentions, read marks, and per-client-session identities; butler-rs does not. Do not share a data dir between them.
